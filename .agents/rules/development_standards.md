# 工程研发与 Git 提交硬性规范 (Development & Git Commit Standards)

## 1. 严格权限控制 (Branch & Push Permissions)
- **绝对禁止擅自推送**: 没有用户的主动明确指示，**绝对禁止**擅自执行 `git push` 推送到 GitHub/GitLab 远程仓库。
- **分支隔离原则**: 所有新功能、Bug 修复和实验性改动，**必须首先拉取独立的实验分支（`exp/...`）** 进行代码实现与自测。
- **合并门禁**: **绝对禁止擅自将实验分支合并到 `main` 主分支**。必须等待用户亲自审核、验收通过并给出明确指令后，方可执行分支合并与远程推送。

## 2. 工程级日志编写规范 (Commit & Merge Logging Standards)
提交日志与合并日志必须达到专业级、企业级、工程级交付标准：
- **结构化呈现**: 严禁敷衍的一句话提交，必须条理清晰、有理有据、有条不紊。
- **功能变更说明**: 简要且专业地提取明确优化了什么功能、新增了什么组件、修改了哪些核心模块，确保任何协作者通过 `git log` 能秒级看懂改动，极大方便未来版本回溯（Rollback）与审计。
- **故障与问题排查归档 (Post-Mortem)**: 如果在实验分支研发过程中遇到了改烂、性能恶化、语法或运行时崩溃（如 RangeError、内存泄漏、渲染死循环等），必须在日志中如实记录问题根因、故障排查过程及终态解决方案，形成可追溯的技术资产。
